# Передача backend тестировщику для ЛР4

Backend готов к отдельному циклу испытаний. В нём есть инженерные unit/integration проверки, OpenAPI-валидация HTTP-ответов и проверки гонок. Они помогают воспроизвести ожидаемое поведение, но не заменяют программу испытаний, независимые результаты и отчёт ЛР4. Frontend пока использует mocks; сквозные browser-испытания следует завершать после его подключения по [передаче frontend-разработчику](frontend-handoff.md).

Основные источники: [README backend](../../backend/README.md), [OpenAPI](../../backend/pkg/api/v1/openapi.yaml), исходное ТЗ команды и утверждённые командой уточнения. Фактический стек: Go 1.25+, Echo, pgx, PostgreSQL 18.6, goose, OpenAPI 3.0.3. Устаревшие упоминания chi/PostgreSQL 16/golang-migrate в ТЗ не являются инструкцией менять среду испытаний.

Текущие границы — `api/v1 → service → repository/postgres`, описаны в [архитектуре backend](../backend-architecture.md). Unit-тесты бизнес-сценариев используют типизированный fake Store и `context` с Principal; HTTP integration-тесты сохранены и проходят через настоящий сервис и PostgreSQL-адаптер. При исследовании дефекта указывайте слой, но проверяйте полное наблюдаемое поведение через API.

## Подготовка воспроизводимого стенда

1. Зафиксируйте commit, ОС, Go/Docker/Compose, ресурсы машины и конфигурацию стенда. Создайте отдельные данные испытаний; не используйте личные аккаунты и рабочую БД команды для сценариев удаления/отката/нагрузки. `config.Load` читает ENV/YAML при запуске и передаёт типизированный Config в конструкторы; после изменения SMTP, ссылок, таймаутов или периодов перезапускайте процесс. В unit-тесте передавайте тестовый Config/Mailer при создании сервиса, не меняйте ENV в ожидании переинициализации уже созданных зависимостей.
2. Из `backend/` выполните `cp .env.example .env`, затем `make up`. Проверьте `/health/live`, `/health/ready`, Swagger `http://localhost:8081`, Mailpit `http://localhost:8025`. Базовый URL: `http://localhost:8080/api/v1`.
3. Создайте первого администратора через `cmd/bootstrap` по README. Создайте хотя бы две дисциплины: индивидуальную 1..1 и командную с ограничениями состава. Подготовьте организатора, назначенного и постороннего судей, капитанов, игроков и постороннего участника. Все обычные аккаунты должны проходить реальное подтверждение e-mail через Mailpit.
4. Автоматические интеграционные тесты запускайте против **отдельной пустой БД**. Пример ниже использует локальные значения `.env.example`; при других логине/порте/пароле измените команду.

```sh
cd backend
docker compose exec -T postgres createdb -U tourneyhub tourneyhub_lr4_test
TEST_DATABASE_URL='postgres://tourneyhub:tourneyhub_local@localhost:5433/tourneyhub_lr4_test?sslmode=disable' make integration-test
```

`createdb` выполняется один раз для нового имени. Не подставляйте `tourneyhub` вместо `tourneyhub_lr4_test`. Тест миграций проверяет up/down и отказывается откатывать БД с прикладными таблицами. API-тесты создают отдельную уникальную схему на сценарий и удаляют только её. Цель `integration-test` включает `-tags=integration -race -count=1` для всех Go-пакетов, включая API, сервисы, библиотеки и миграции.

Остальные проверки:

```sh
make check build docs
```

`make check` включает воспроизводимость генерации HTTP-кода/DTO mapping, unit-тесты, архитектурные AST-проверки и vet. Бизнес-методы сервисов не должны импортировать Echo/OpenAPI/pgx или содержать SQL, а runtime-чтение ENV находится только в `internal/config`. Проверка этих ограничений не заменяет реальную проверку транзакционных инвариантов.

Сохраните логи и exit codes. Для измерения покрытия в ходе ЛР4 можно выполнить отдельный запуск `go test -tags=integration -race -coverpkg=./internal/... -coverprofile=build/lab4/coverage.out ./...` с тем же `TEST_DATABASE_URL`, предварительно создав `build/lab4/`. Отчёт `go tool cover -func=build/lab4/coverage.out` показывает долю выполненных операторов Go, а не покрытие всех ветвей; процент сам по себе не доказывает корректность сценариев. Границы пакетов и состав запуска укажите вместе с процентом. Общий -coverpkg учитывает исполнение сервисов, моделей и репозиториев из HTTP-тестов; без него покрытие зависимостей из другого test binary может не учитываться.

## Карта функциональных и негативных испытаний

Для каждого случая задайте: идентификатор, требование/операцию OpenAPI, роль и отношение к объекту, начальное состояние, входные данные, шаги, ожидаемые HTTP/status/body и изменения данных, фактический результат и доказательство. Один HTTP 200 без проверки состояния после операции недостаточен.

| Группа | Положительные случаи | Негативные и граничные случаи |
| --- | --- | --- |
| Регистрация и login | Согласие, письмо, одноразовое подтверждение, подтверждённый вход | Нет согласия; дубликаты e-mail/nickname с другим регистром; неподтверждённый/заблокированный аккаунт; неверный пароль; шестая попытка за минуту; 12 символов и граница 72 байт bcrypt, многобайтовый UTF-8 |
| Токены | Access/refresh, истечение, ротация, logout, reset всех сессий | Произвольный/просроченный/повторный токен; чужой logout; повтор consumed reset/verify; роли изменены после выдачи токена; поддельные forwarded IP |
| Команда | Капитан и членство атомарны, оба вида приглашений, передача прав | Чужая команда, повторное/просроченное/отозванное приглашение, неправильный секрет, исключение капитана без передачи, устаревшая version, ограничения personal team |
| Турнир | Draft без дат, заполнение, публикация, фильтры/пагинация, отмена | Неверный IANA-регион; `opens >= closes`, `closes > starts`, `starts >= ends`; несовместимые группы/wildcard/серия; чужой организатор; скрытый/draft/удалённый ресурс; изменение регламента активного турнира |
| Заявка | Капитан, снимок состава, принятие, отказ с причиной, отзыв | Время ровно открытия/закрытия; полный турнир; не член команды; слишком мало/много игроков; один игрок в двух командах; дубликаты UUID; повторная заявка; изменение команды не меняет исторический снимок |
| Жеребьёвка | Elo/random/manual, сохранённый preview, confirm повторно, перестроение до результатов | Не полная перестановка manual, чужой preview, просроченный preview, stale tournament version, мало участников, изменение принятых заявок после preview, перестроение после начала результатов |
| Форматы | 2/3/4/5 участников, нечётные круги, 1/2 круга, группы змейкой, wildcard, третье место | Bye не получает результат/Elo; места и выходящие при равных очках; граничное число групп; 256 участников; правильные ссылки победителя/проигравшего |
| Расписание | Матч/тур целиком, площадка или online URL, судья матча/турнира | Пересечение игрока через разные команды/турниры, пересечение судьи, соседние часовые слоты, выход за даты турнира, матч раньше зависимого, перенос завершённого матча, отказ всей пачки при одном конфликте |
| Результат | Bo1/Bo3/Bo5, подтверждение другой стороной, автоподтверждение | Ввод до старта, неверное число/порядок партий, серия не закончилась/сыграна после победы, ничья в плей-офф, own-side confirm, посторонний капитан, stale match version, повтор фиксации |
| Спор и коррекция | Открытие, назначенный судья, мотивированное решение | Посторонний судья, повтор спора, пустая причина, изменение победителя после старта зависимого матча; корректировка без изменения победителя; корректный пересчёт более поздних Elo |
| Рейтинг и места | 1500, K=32, история, нулевая сумма дельт, завершение этапов | Повторная фиксация не начисляет Elo повторно; draw/bye; сортировка равных рейтингов; последующие турниры после коррекции; нет преждевременного завершения/потери мест |
| Файлы | PNG/JPEG/PDF, UUID вложения, точные байты скачивания | 0/5 МиБ/5 МиБ+1; поддельный MIME/сигнатура; PDF avatar; повреждённое изображение; чужой/private protocol; новый капитан вне снимка состава; traversal/Unicode/длинное имя |
| Уведомления и SMTP | Нужный адресат, собственный список, read идемпотентно, retry | Чужой notification ID; отключённый e-mail; SMTP недоступен/без STARTTLS/таймаут; повтор доставки после сбоя; секрет не остаётся в payload после успешной отправки |
| Администрирование | Дисциплины, роли, блокировка/разблокировка, модерация и аудит | Потеря последнего активного подтверждённого admin; параллельные удаления ролей/блокировки; обычный участник вызывает admin API; отсутствие секретов в аудите |
| SSE и CSV | Именованные события, heartbeat, Last-Event-ID replay, итоги completed | Повтор reconnect без потерь/дубликатов обработки; недоступный cursor/resync; скрытие/удаление закрывает поток; отключение клиента; CSV названия с `= + - @`, запятыми, кавычками и переносами |

Для проверки автоподтверждения не нужно ждать сутки: используйте изолированные fixtures с истёкшим `confirmation_deadline` и вызов `service.AutoConfirm` в Go-тесте. В проверке запущенного сервиса отдельно дождитесь очередного фонового прохода (`worker.interval`, по умолчанию минута). Для сокращённого тестового периода задайте `WORKER_INTERVAL`/YAML до старта стенда. Любое тестовое изменение времени/SQL-фикстуры запишите в методике и применяйте только к тестовым данным.

## Конкурентные сценарии

Запускайте действия одновременно с барьером старта и повторяйте их на свежих данных. Проверяйте итог БД и отсутствие частичных обновлений:

1. Два refresh с одним токеном: успешна одна ротация, второй запрос отвергается; существует одна действующая новая пара.
2. Принятие двух заявок на последнее место: ровно одно принятие, второй запрос получает 409, вместимость не превышена.
3. Заявки одного игрока от разных команд: только одна активная reservation; отказ/отзыв освобождает её атомарно.
4. Confirm против dispute против фонового AutoConfirm: одна согласованная ветка результата, одна версия, без двойного Elo/продвижения.
5. Два переноса/назначения судьи на конфликтующие интервалы, включая разные турниры: конфликт отсекается; пакет тура откатывается целиком.
6. Два изменения одной version и одновременная смена капитана: устаревшее изменение получает 409/теряет право; прежний автор результата не может подтвердить свою сторону через нового капитана.
7. Параллельное лишение ролей/блокировка последних администраторов: остаётся хотя бы один активный подтверждённый admin.
8. Два background worker: задания SMTP захватываются через SKIP LOCKED; допустимый повтор при сбое доставки учитывается отдельно от потери письма.

Детектор Go `-race` проверяет гонки памяти процесса. Он не заменяет эти проверки транзакционных инвариантов PostgreSQL.

## Сквозные сценарии после подключения frontend

Используйте разные browser contexts для аккаунтов; сохраните трассу Playwright/скриншоты и сетевые ответы.

1. Регистрация → Mailpit → подтверждение → login → профиль/аватар → reload → logout; отдельно reset пароля и недействительность старой сессии.
2. Капитан создаёт команду → приглашает игрока → игрок принимает → капитан передаёт права; прежний капитан теряет управляющие действия.
3. Организатор создаёт draft → публикует → капитаны подают заявки → организатор принимает → закрывается регистрация → preview/confirm сетки → расписание.
4. Капитан сообщает результат с файлом → соперник подтверждает; сетка/таблица/Elo обновляются в другом открытом browser context по SSE.
5. Соперник оспаривает → назначенный судья решает → итоговые данные совпадают у всех ролей; посторонний аккаунт не скачивает протокол и не решает спор.
6. Последний матч завершает турнир → итоговые места → CSV; отдельно groups_playoffs и round_robin, часовой пояс вне зоны браузера, конфликт двух вкладок с одной version.
7. Администратор скрывает турнир → каталог/карточка/поток зрителя перестают выдавать ресурс; организатор получает уведомление.

Пока эти действия выполняются только через Swagger/API либо frontend всё ещё показывает mocks, отмечайте browser-кейсы как не выполненные и указывайте зависимость от frontend. Скриншот макета не является доказательством интеграции.

## Нагрузочные и эксплуатационные испытания

В ТЗ указаны ориентиры: p95 API ≤ 300 мс при 200 запросах/с, 1000 одновременных пользователей, генерация на 256 участников ≤ 2 с, первая загрузка страницы ≤ 3 с при канале 10 Мбит/с. Перед приёмкой команда должна подтвердить применимость этих требований и ресурсы стенда; текущие инженерные тесты не подтверждают их выполнение.

Для k6 зафиксируйте точную версию/образ по версии или digest, сценарий, dataset, настройки БД/API и оборудование. Выполните разогрев, основной профиль 200 RPS со стабильным набором чтений/записей, отдельный профиль 1000 сессий и длительных SSE, затем отдельный замер генерации 256 участников для трёх форматов. Публикуйте p50/p95/p99, throughput, ошибки, время генерации, CPU/RAM, число соединений БД и параметры пула. Токены подготовьте заранее; лимит login 5/min/IP иначе исказит нагрузку на бизнес-операции. При истечении access включите штатный refresh.

Для browser-профиля измерьте первую загрузку без прогретого кеша и с ограничением канала. Отдельно проверьте SIGTERM/graceful shutdown, недоступность БД и readiness 503, перезапуск, сохранение данных, миграцию и восстановление из резервной копии. TLS, backup/WAL и заявленные SLA зависят от развёртывания: проверяйте реально настроенный стенд и не переносите эти гарантии на локальный Compose автоматически.

При проверке таймаутов берите фактический Config стенда. Defaults: `http.read_header_timeout=5s`, `read_timeout=15s`, `idle_timeout=60s`, `shutdown_timeout=10s`, `body_limit=6M`; SMTP dial/общий timeout — 10s/15s; SSE poll/heartbeat — 1s/15s; retention — 168h. HTTP WriteTimeout не установлен для длительного SSE. Секреты и разрешение локального insecure SMTP загружаются только через `config`; у SMTP-клиента нет отдельного чтения ENV. Изменения значений между прогонами требуют пересоздания зависимостей и отражаются в протоколе испытаний.

## Материалы для отчёта ЛР4

- Программа и методика испытаний с трассировкой требований к case IDs, предварительными условиями и критериями успешности.
- Версии/commit/ресурсы/конфигурация стенда, способ подготовки и очистки данных, команды воспроизведения.
- Реестр результатов: passed/failed/not run, фактический результат, issue для дефекта, исправление и повторная проверка. Инженерные тесты разработчика укажите отдельным источником, а собственные независимые испытания — отдельной группой.
