# TourneyHub Backend

Серверная часть TourneyHub: Go, Echo, pgx, PostgreSQL 18 и goose. Все пути ниже относятся к директории `backend/`. Команды Make работают и из неё, и из корня репозитория.

Реализованы контракты и инфраструктура: запуск, миграции, health checks, публикация OpenAPI и расчёт Эло. **Все бизнес-ручки пока возвращают `501 not_implemented`**. Аутентификация тоже возвращает 501 и не принимает произвольные токены. Алгоритмы сеток, авторизация, SMTP, хранение файлов, SSE и фоновое подтверждение результатов описаны как будущая реализация.

## Запуск

Нужны Docker Compose и Make. Локальный Go нужен только для генерации, тестов и GoDoc.

```sh
cd backend
cp .env.example .env
make up
```

Корневой Makefile передаёт команды в backend: из корня также работают `make up`, `make generate`, `make check` и остальные цели. Имя Compose-проекта закреплено как `tourneyhub`, поэтому перенос конфигурации в `backend/` сохраняет существующие контейнеры и volume PostgreSQL.

`make up` ждёт готовности PostgreSQL, собирает образ, запускает `cmd/migrate up` как отдельный Compose-сервис и разрешает запуск API только после успешного завершения миграций. Ошибка миграции останавливает запуск. SQL читается с диска из директории `migrations.directory` в YAML; goose использует advisory lock PostgreSQL. Compose монтирует `config/` и `migrations/` для сервиса миграций с доступом только на чтение. Повторный `make up` безопасен: применяются только новые версии.

По умолчанию:

- API: http://localhost:8080; readiness: `/health/ready`, liveness: `/health/live`.
- Swagger UI: http://localhost:8081; читает спецификацию с API, поддерживает Try it out.
- PostgreSQL: `localhost:5433`; учётные данные для локальной разработки — в `.env.example`.

Порты контейнеров меняются через `API_PORT`, `SWAGGER_PORT`, `POSTGRES_PORT` в `.env`. Все публикуемые порты привязаны к loopback. Изменение `DB_USER` или `DB_PASSWORD` не меняет учётные данные уже инициализированной БД: для существующего volume их нужно менять в PostgreSQL.

## Конфигурация

[`config/config.yaml`](config/config.yaml) содержит HTTP-адрес, CORS, адрес/порт/имя PostgreSQL, режим SSL и путь к SQL-миграциям. `CONFIG_PATH` позволяет выбрать другой файл. Относительный `migrations.directory` считается от директории YAML-файла; значение `../migrations` указывает на `backend/migrations`.

`DB_USER` и `DB_PASSWORD` обязательны и читаются только из окружения; поля секретов в YAML запрещены. Строка подключения формируется программно с экранированием логина и пароля. Make экспортирует значения из локального `.env`, Compose передаёт их контейнерам.

Для контейнеров Compose переопределяет `DB_HOST=postgres`, `DB_PORT=5432`, `HTTP_ADDRESS=:8080` и CORS под порт Swagger UI. При запуске на хосте используются параметры YAML. Их можно переопределить через `DB_HOST`, `DB_PORT`, `HTTP_ADDRESS`, `CORS_ALLOWED_ORIGINS`; например, при смене `POSTGRES_PORT` укажите тот же `DB_PORT` для `make run`.

```sh
make logs
make migrate-status
make down
```

`make down` сохраняет данные. `make migrate-down` откатывает одну последнюю миграцию и удаляет соответствующие данные; использовать только при осознанном откате.

Для запуска Go-процесса на хосте при уже работающем PostgreSQL: `make run`. Make читает `.env`, сначала применяет миграции, затем запускает API. Выберите свободный `HTTP_ADDRESS`, если Compose API тоже запущен. Сервис завершает HTTP-запросы при SIGINT/SIGTERM.

## Контракты и структура

Источник истины: [`pkg/api/v1/openapi.yaml`](pkg/api/v1/openapi.yaml). 73 операции: аккаунты, команды/приглашения, дисциплины, турниры/заявки, посев, расписание, результаты/споры, рейтинг, вложения, уведомления и администрирование. Каждая операция содержит описание; `x-required-roles` документирует необходимые роли.

```text
cmd/api                 точка запуска API
cmd/migrate             up / down / status
config/config.yaml      настройки сервиса без секретов
internal/app            жизненный цикл Echo и graceful shutdown
internal/container      сборка зависимостей, пул pgx
internal/config         загрузка YAML и секретов из окружения
internal/api/v1         реализация сгенерированного ServerInterface
internal/model          доменные значения; пример Эло
internal/migration      чтение SQL с диска и provider goose с блокировкой
pkg/api/v1              OpenAPI, конфигурация генератора, api.gen.go
migrations              001_identity.sql ... 006_notifications_audit.sql
```

Структура повторяет разделение `cmd → app/container → api → service → repository` из transportgate. По мере реализации сценариев интерфейсы бизнес-логики добавляются в `internal/service`, SQL — в `internal/repository`; HTTP DTO преобразуются в доменные модели на границе. Эти слои пока не заполнены искусственными интерфейсами.

```sh
make generate
make check
make build
```

Go 1.25+, `oapi-codegen` **v2.6.0** закреплён в `go.mod` через `tool`. Генерируются модели, Echo ServerInterface/маршруты и встроенная спецификация. `api.gen.go` коммитится; редактировать его вручную нельзя. Шаблоны в `pkg/api/v1/templates/` переводят комментарии генератора на русский и подключены в `oapi-codegen.yaml`. После изменения контракта компилятор требует реализовать новые методы в `internal/api/v1`. `make generate-check` сравнивает результат повторной генерации с сохранённым файлом. Echo middleware проверяет тело, параметры, UUID и ограничения по спецификации. Ошибки имеют единый формат `{code, message, request_id, details?}`.

**Отличия от ТЗ:** Echo вместо chi; goose вместо golang-migrate; PostgreSQL 18 вместо 16; OpenAPI **3.0.3** вместо 3.1. Последний выбор связан с отсутствием штатной поддержки 3.1 у закреплённого [oapi-codegen v2.6.0](https://github.com/oapi-codegen/oapi-codegen/tree/v2.6.0#does-oapi-codegen-support-openapi-31). Контракт не использует возможности JSON Schema 2020-12, поэтому последующая миграция на 3.1 не меняет HTTP-поведение.

## Схема БД и правила реализации

Миграции разделены на учётные записи/файлы, команды, турниры/заявки, сетку/таблицы, результаты/рейтинг и уведомления/аудит. В каждой есть goose Up и Down. Даты — `timestamptz`, доменные ID — UUID, версии — положительные bigint. Пароли и одноразовые/refresh-токены хранятся в виде хешей. Команды и турниры удаляются мягко для сохранения истории.

Состав заявки хранится снимком в `application_players`. Отдельная `tournament_player_claims` с PK `(tournament_id, user_id)` резервирует игрока только для pending/accepted заявки; сервис создаёт и освобождает резерв в той же транзакции, что меняет заявку. Капитан обязательно состоит в команде: связь проверяется отложенным FK при commit. Составные FK запрещают привязывать матч, группу, участника или протокол к чужому турниру/матчу. Регламент содержит снимок ограничений дисциплины.

Проверки, зависящие от роли, времени, соседних записей и алгоритмов, остаются обязанностью будущего сервисного слоя: вместимость, размер состава, допустимость ничьей, переходы статусов, формат серий, конфликты расписания, защита последнего администратора и запрет изменения активной сетки. Для optimistic locking SQL обновляет запись через `WHERE id = $1 AND version = $2`, увеличивает version; отсутствие обновлённой строки даёт 409.

Фиксация результата должна одной транзакцией изменять матч, сетку/таблицу, Эло обеих команд, этап/турнир и аудит, добавлять уведомления/outbox. Блокировки применяются в стабильном порядке. Автоподтверждение после deadline и спор конкурируют за ту же версию матча. Outbox и таблица событий предусмотрены для SMTP и SSE; обработчики ещё не реализованы. При коррекции завершённого результата нужно пересчитывать последующие рейтинги; изменение победителя после старта зависимого матча запрещено.

## Документирование кода

Комментарии написаны на русском по правилам GoDoc. Пример: [`internal/model/rating.go`](internal/model/rating.go), описание пакета — в `doc.go`. Есть краткое и подробное описание типов, полей, конструктора и метода, аргументов, результата и ошибок. `MatchRating` встраивает `EloRating`, демонстрируя композицию типов.

```sh
go doc -all ./internal/model
make docs
```

Встроенная команда `go doc` читает комментарии и создаёт `build/docs/example.txt`. Отдельного приложения для разбора исходников нет.

Для HTML и RTF используется Pandoc: это преобразование вывода `go doc` в нужный формат. Установить его на macOS можно командой `brew install pandoc`, в Ubuntu — `sudo apt-get install pandoc`.

```sh
make docs-export
make docs-serve
```

`docs-export` создаёт `build/docs/index.html` и `example.rtf`, добавляет ссылку на копию исходного файла `_source/rating.go`. `docs-serve` использует стандартный HTTP-сервер Python 3 для папки `build/docs`; документация доступна на http://127.0.0.1:6060/. Подготовленный вывод также можно открыть локально без сервера.

Executable example в тесте демонстрирует переход 1500 → 1516 после победы над равным соперником. Метка `Output:` нужна инструментам Go и сохраняется на английском, как и `Code generated` в сгенерированных файлах.

## Служебные директории

- `build/` — результаты генерации документации; папка игнорируется Git и пересоздаётся командами Make.
- `bin/` — собранные бинарники API и миграций; также игнорируются Git.
- `.github/workflows/backend.yml` в корне репозитория — GitHub Actions: автоматические проверки, сборка, GoDoc и интеграционный тест миграций при push и PR.

## Проверки

`make check` проверяет воспроизводимость генерации, загрузку YAML/секретов, пути миграций, HTTP-контракт, единый формат ошибок, readiness, расчёт Эло и `go vet`. CI повторяет проверки, сборку, генерацию документации и интеграционные миграции.

Для интеграционного теста нужна **отдельная пустая БД**. Пример при запущенном Compose:

```sh
docker compose exec -T postgres createdb -U tourneyhub tourneyhub_test
make migration-test TEST_DATABASE_URL='postgres://tourneyhub:tourneyhub_local@localhost:5433/tourneyhub_test?sslmode=disable'
```

Тест проверяет `up → повторный up → down → up → down`, ограничения размера файла, уникальности никнейма, членства капитана и повторной заявки одного игрока. При обнаружении существующих прикладных таблиц тест отказывается выполнять откат. Рабочую БД передавать сюда нельзя.
